# EasyMail からフォーム・履歴・添付を移行する

公式配布版 2.00.124・2.00.125・2.00.133・2.01.004 のテーブル構成と、同じ版から取得した設置ファイルのバックアップが対象です。旧アプリの PHP を起動せずに取り込めます。別の版や独自改修のある場合は、まず複製環境で差分を確認してください。[公式 2.00.133](https://www.mubag.com/download/2.00.133/EasyMail_2.00.133.zip)・[公式 2.01.004](https://www.mubag.com/download/2.01.004/EasyMail_2.01.004.zip)

設置版の番号は管理画面かバックアップで確認できます。[旧サーバーで版番号を調べる](EASYMAIL-VERSION.md)

<a id="easymail-200125"></a>

## 2.00.125・2.00.124 の旧サイトを移す場合

**どちらの版も、稼働している版のまま直接移行できます。** 初回の練習と切替当日の最終取込には、それぞれ同じ時点の旧 DB ダンプと実際の `em_laravel` のファイル・添付を使います。MailForm はバックアップを読み取るので、旧側の PHP 7.4 や Laravel 6 の更新、中継用の 2.00.133 の起動は不要です。

- **設置URL**。旧管理画面が `https://www.example.jp/admin` なら、簡単設置に入力するのは `https://www.example.jp` です。`em_laravel` はコピー元のディレクトリ名です。個別フォームの URL は旧 DB の `forms.url` から引き継ぎます。
- **版と必須列**。公式配布物の `forms`、`form_blocks`、`form_items`、`choices`、`histories`、`plugins` の定義は両版と 2.00.133 で一致し、取込に必要な計42列があります。`cache` はこの系列の標準テーブルです。旧管理者は新サーバーで作成します。
- **設置ファイルの照合**。各版の公式 ZIP から183ファイル分の SHA-256 を採取しました。運用していたファイルをその版の一覧と比較するため、旧バックアップの版番号やファイルは原本のまま使ってください。[公式 2.00.125](https://www.mubag.com/download/2.00.125/EasyMail_2.00.125.zip)・[2.00.125 の照合一覧](../resources/easymail/2.00.125-sha256.json)・[公式 2.00.124](https://www.mubag.com/download/2.00.124/EasyMail_2.00.124.zip)・[2.00.124 の照合一覧](../resources/easymail/2.00.124-sha256.json)
- **郵便番号付き住所**。取り込んだフォームでは旧版と同じ `zip`、`pref`、`address` の入力名を使用します。住所を含む代表フォームで入力・確認・完了まで試し、メールと CSV でも表示を照合してください。
- **添付を使うフォーム**。取込後は履歴から実ファイルを開き、旧コピーと件数・SHA-256 を照合します。新規受付時、両旧版は利用者への自動返信にも添付を送っていました。MailForm は添付を管理者通知に送り、利用者への自動返信は本文のみを送ります。既存の案内文が添付の返信を約束している場合は切替前に見直してください。

両版の公式テーブル定義と模擬データを使い、MariaDB 10.6.28 のダンプを新しい AlmaLinux 10.3 の MariaDB 11.8.8 に復元して検証しました。各版100フォーム（公開99・非公開1）を取り込み、最終コピーの旧履歴101件・添付11件が一致しました。再取込後も件数は同じで、過去の履歴から作成された配信は0件でした。実際の切替では、ご自身の旧 DB の件数と印刷物・Webサイトで使っている URL を基準に照合します。

## 独自テーマを引き継ぐ

2.00.124・2.00.125・2.00.133・2.01.004 で共通です。バックアップには `resources/views/theme` をディレクトリごと含めます。たとえば旧フォームが `garden` を使っていれば、`resources/views/theme/garden` と標準テーマを一緒にコピーします。フォームの公開URLはこれまでどおり旧DBの `forms.url` で決まります。標準5種と同じ名前のディレクトリを直接改変した場合は、従来の標準ファイル差分として報告され、対象フォームは保留になります。

1. **診断する。** 簡単設置の取込スクリプトは最初に診断します。手動の場合は `php artisan easymail:import --dry-run --strict --source-root=/backup/EasyMail --json` です。`themes` の下に独自テーマごとの `layout`（推定した元テーマ）、`score`（同じ相対パス・SHA-256の数）、`changes`（変更・追加・削除）、`behaviors`（旧画面やメール・JSの変更）、`warnings` が出ます。最多が同数の場合は候補を表示し、名前順で選んだレイアウトをプレビューできます。一致が0件、バックアップが読めないなどの場合、該当フォームは公開保留です。
2. **管理画面で比べる。** 管理者で「テーマ管理」を開き、対象テーマの「編集」→「移行時の差分」を見ます。「プレビューと公開」でフォームのプレビューを開き、旧サイトと並べて、ロゴ、色、余白、ヘッダー・フッター、スマートフォン幅での表示を確認します。プレビューは閲覧専用です。「CSS・画像」では取り込まれた内容を確認・差し替えできます。ヘッダーのロゴと本文もこの画面で編集できます。
3. **動作の差を判断する。** たとえば `js/ad_cookie.js`、`js/jquery.emform.js`、`form.blade.php`、完了・メールのテンプレートの差分は一覧に残ります。旧サイトの計測、入力補助、メール文面が業務に必要か判断し、必要なものは切替前にMailForm側で設定・実装して確認します。
4. **照合を完了する。** 「移行時の差分と表示を確認しました」にチェックし、「確認を完了して対象フォームを公開」を押します。このテーマのうち、旧側で公開中かつ他の診断を通ったフォームが旧URLで開くようになります。旧側で非公開のフォームは下書きのままです。練習環境では、ここで初めて実際の入力・確認・送信まで試せます。

| バックアップの内容 | MailFormへの反映 |
| --- | --- |
| コンパイル済みのCSS | 変更・追加された `css/` のCSSを解析します。構造を引き継ぐテーマでは、旧レイアウトが読み込んでいた標準CSSも検査し、元の順で適用します。同じ内容のファイルはテーマ間で共有します。ローカル画像、対応する旧ブラウザー用の指定、カンマ区切りのメディアクエリの対応条件を引き継ぎます。外部URL、`@import`、未対応の記述は種類別に件数と代表位置を表示します。 |
| SVG・PNG・JPEG・GIF・WebP | 実体を検査し、同じ内容はテーマ間でも1つの非公開ファイルを共有します。SVG は Illustrator の編集用属性を除き、図形内で参照される日本語 ID とその参照を書き換えます。スクリプト、イベント属性、外部参照、禁止要素を含む SVG はファイル単位で除外し、警告に表示します。 |
| ヘッダー・フッター・レイアウト | 静的な文言・書式と既知の画像参照を下書きにします。ロゴがヘッダーのリンクの CSS 背景として指定されている場合も、対応する画像と画面幅ごとの大きさを引き継ぎます。除外したBlade・PHP・スクリプトはファイル名と行番号を表示します。旧コードは実行しません。 |
| 入力・確認・完了の画面構造 | 表題や項目名、入力値、住所欄、ボタン文言の位置を手がかりに、各部品を囲む要素・クラス・IDを読み取ります。MailForm が自分のフォーム、入力チェック、送信処理を使って描画します。入力欄には旧DBの項目別CSSクラス・IDも反映します。 |

### ロゴは表示されるが本文の見た目が違うとき

1. 以前の版で取込済みなら、練習環境を `setup.sh update-preview` で更新し、同じバックアップで `import-backup.sh` を再実行します。取込の際にテンプレートを読み直すので、移行元と同じ時点の設置ファイルとDBを指定してください。
2. **「テーマ管理」→「編集」→「移行時の差分」** で「部品ごとの推定結果と適用状況」を開きます。推定した部品にはファイル名と行が表示されます。個別に推定できなかった部品は、共通の部品設定または標準の表示を使います。コマンドのJSONでは各テーマの `structure`、`structure_sources`、`structure_fallbacks` に対応します。
3. 「プレビューと公開」から、同じフォームの入力・確認・完了を旧サイトと見比べます。PC幅とスマートフォン幅で、項目名と入力欄の並び、必須印、選択欄、住所、戻る・送信ボタンを確認します。住所の建物名を番地と同じ欄に入力していたフォームは、そのまま使えます。建物名が独立した欄として推定されたテーマは、入力した建物名も住所の回答に含めます。
4. 直したい部品を選んで「部品を表示」を押します。タグ、CSSクラス、ID、外側から順に並ぶ枠を調整し、「この部品を保存」してプレビューを開き直してください。「標準の構造を使う」も部品ごとに指定できます。手直しは通常の再取込と練習から本番への引継ぎで保持されます。「取込時の推定に戻す」で、その部品を再び自動更新できます。

旧JavaScriptの動作、外部のフォント・画像、動的に組み立てるHTMLは画面によって差が残ります。郵便番号からの住所検索はMailFormの機能で動作します。プレビューでの確認後、練習用URLでも入力、戻る、送信を試してください。

**最終取込の既定は「手直しを残す」です。** 再取込では、管理画面で編集した文面・CSS・画像などを保ち、手を加えていないものを新しいコピーから更新します。旧テーマのファイルが変わったとき、または管理画面で見た目を変更したときは、再び「照合待ち」になります。同じバックアップを繰り返しても、完了した照合は維持されます。

手直しを破棄して旧コピーの内容に戻すときだけ、取込コマンドに `--overwrite-themes` を付けます。簡単設置の場合は次の位置です。元の公開URL・履歴・添付の照合はどちらのモードでも行います。

```bash
sudo bash MailForm/deploy/almalinux10/import-backup.sh --overwrite-themes /srv/mailform-import/final/backup.sql /srv/mailform-import/final/EasyMail
```

検証では4版それぞれの公式テーマをコピーし、架空のロゴ、CSS、ヘッダー、JSとメールの変更を加えました。別途、AlmaLinux 10.3・MariaDB 11.8.8 では、MariaDB 10.6.28 で取得した模擬ダンプを使い、`/root` からの取込、練習で編集したフッターの本番への引継ぎ、最終コピーのCSS変更による再照合、旧公開URL・履歴・添付の一致まで確認しました。

## 簡単設置で使うバックアップを用意する

初回は旧サイトで受付を続けた状態のコピーを使います。切替当日は受付・編集と処理中の送信を止め、同じ手順で新しく `final` を作ります。以下は SSH で両サーバーを管理できる場合の例です。管理会社に依頼する場合も、単一 DB の SQL と、下記のファイルを同じ時点で取得してください。

**旧サーバーで**、読み取り用のDBアカウントでダンプを取得します。`旧DB名`、`旧DBユーザー` と設置ディレクトリを実際の値に置き換えてください。古い MySQL では対応する `mysqldump` を使えます。SQL は対象DBのテーブルとデータだけを含む形式にします。DB選択・作成、トリガーやルーチンを含むダンプの場合は、元環境でエクスポートし直します。

```bash
umask 077
copy="$HOME/mailform-first"
mkdir -m 700 "$copy"
mariadb-dump -u 旧DBユーザー -p --single-transaction --quick --hex-blob --skip-triggers 旧DB名 > "$copy/backup.sql"
cd /旧EasyMailの設置ディレクトリ
files=(config/app.php config/append.php app/Http/Controllers/IndexController.php app/Library/Common.php app/Mail/ContactMail.php routes/web.php resources/views/theme resources/lang)
if test -d storage/app/attach_file; then files+=(storage/app/attach_file); fi
tar -czf "$copy/EasyMail.tar.gz" -- "${files[@]}"
```

`config/app.php` が `em_laravel` の下にあれば、その内側で実行します。各コマンドの成功を確認し、**手元の PC で**次を実行します。`scp -3` は両方のサーバーに手元の SSH 鍵で接続し、2ファイルを PC 経由で転送します。SFTP クライアントでの転送も可能です。

```bash
ssh 管理者@新サーバーのIP 'umask 077; mkdir "$HOME/mailform-first"'
scp -3 旧SSHユーザー@旧サーバー:mailform-first/backup.sql 旧SSHユーザー@旧サーバー:mailform-first/EasyMail.tar.gz 管理者@新サーバーのIP:mailform-first/
```

**新サーバーで**、練習環境の設置後に実行します。展開は SSH で入った一般ユーザーが行います。専用の非公開領域には通常のファイルとディレクトリをコピーします。

```bash
cd ~/mailform-first
mkdir -m 0700 EasyMail && tar --no-same-owner --no-same-permissions -xzf EasyMail.tar.gz -C EasyMail
dest=/srv/mailform-import/first
sudo dnf install -y rsync
(
  set -e
  sudo install -d -o root -g mailform -m 0750 /srv/mailform-import
  sudo mkdir -m 0700 "$dest"
  sudo chgrp mailform "$dest" && sudo chmod 0750 "$dest"
  sudo install -d -o root -g mailform -m 0750 "$dest/EasyMail"
  sudo install -o root -g root -m 0600 backup.sql "$dest/backup.sql"
  sudo rsync -rpog --chown=root:mailform --chmod=D750,F640 --exclude='.env*' EasyMail/ "$dest/EasyMail/"
)
```

取り込む回ごとに空の保存先を使います。最終コピーはすべての `first` を `final` に替えます。新サーバーで `cd ~` して[簡単設置の取込手順](ALMALINUX10.md#3-旧データのコピーで練習する)へ戻ります。

`import-backup.sh` は実行ごとに別名の複製DBを作り、読み取り専用アカウントで診断・取込・全件照合を行います。フォーム別の警告・公開保留がある場合も下書きで取り込み、履歴と添付まで照合します。全体を停止するのは、添付の欠損、URL 衝突、旧 DB の必須列不足など、データの完全性に関わる問題です。複製DB名と管理者用の照合記録の場所は実行結果に表示されます。転送ファイルと複製DBの保持期限も、元のバックアップと合わせて管理してください。MariaDB 10.6 系のダンプで現れる `@@sql_notes` の廃止予告（1287）は復元ログに残して継続します。その他の復元警告やエラーは停止して確認します。[MariaDB の廃止予告](https://mariadb.com/docs/release-notes/community-server/changelogs/11.4/11.4.1)

## 準備

1. 旧データベースのバックアップを専用の DB に復元し、対象テーブルを SELECT できる読み取り専用ユーザーを用意します。旧サイトの添付・テーマ・設置ファイルは公開ディレクトリの外に展開します。
2. MailForm の新 DB を用意し、通常のインストール手順に従って `php artisan migrate --force` を実行します。移行元の接続先を MailForm の `.env` に設定します。下の DB 名とユーザー名は例です。
3. バックアップ内の `resources/views/theme` と `storage/app/attach_file` の位置を確認します。2.00.124・2.00.125・2.00.133 は設置先の `em_laravel` 内に、2.01.004 は EasyMail 直下に両方があります。EasyMail のルートディレクトリを `--source-root` に渡します。添付を別の場所に復元した場合は `--attachments` で上書きできます。運用時は認証情報、旧版コード、診断 JSON を公開領域外で保管してください。

```dotenv
LEGACY_DB_DRIVER=mariadb
LEGACY_DB_HOST=127.0.0.1
LEGACY_DB_PORT=3306
LEGACY_DB_DATABASE=easymail_snapshot
LEGACY_DB_USERNAME=easymail_reader
LEGACY_DB_PASSWORD=
```

MySQL は `LEGACY_DB_DRIVER=mysql` に設定します。ローカルソケットは `LEGACY_DB_SOCKET` で指定できます。設定キャッシュを使用している環境では、変更後に `php artisan config:cache` を実行してください。

移行コマンドは接続中のDBを確認します。同じサーバー・同じDB名を指す接続は、ユーザーやホストの別名が違っても終了コード1になります。同一の新DBに対する取込・事前診断・照合は同時に1本だけ実行できます。二重起動は待機せず終了コード1になります。

## 事前診断

```sh
php artisan easymail:import --dry-run --source-root=/backup/EasyMail
php artisan easymail:import --dry-run --source-version=2.00.133
php artisan easymail:import --dry-run --form=5 --source-root=/backup/EasyMail --json
```

`--dry-run` は既存の新 DB も参照して URL 衝突を調べ、DB と添付ストレージへの書き込みを省きます。JSON はフォームごとの元 ID・公開パス・可否・項目数・履歴件数・照合できた添付件数・理由を返します。`--strict` の終了コードは次のとおりです。

| 終了コード | 確認すること |
| --- | --- |
| 0 | 診断・取込が完了しました。フォーム別の `issues`・`warnings` は、そのフォームを下書きにした理由です。履歴だけのフォームも件数と照合に含みます。 |
| 2 | URL 衝突、旧 DB の構造不一致、参照された添付の欠損、取込済みデータとの照合差異などがあります。`integrity_errors`、各フォームの `integrity_errors`、照合時の `reconciliation` を確認します。簡単設置では SQL の復元失敗も 2 です。 |
| 1 | 接続・権限・引数・排他などの実行エラーです。表示されたエラーを確認します。 |

たとえば、安全な HTML 装飾の目視確認、自動返信用の email 項目不足、旧履歴が標準の JSON 配列ではない場合は、該当フォームを下書きにして全件照合に進みます。元の定義が削除されたフォームの履歴も保管します。テーマを照合しても、個別の確認が必要なフォームは下書きのままです。

- 5 種類の標準テーマを認識します。設置ファイル指定時は選択テーマの配布ファイル、本体の公開処理・ルート・拡張ポイント設定等の SHA-256 を公式 ZIP 基準で照合し、欠損・追加・変更の相対パスを出します。標準テーマ名で上書きされたテンプレートも検出対象です。旧 Blade・PHP・JavaScript は実行しません。
- 設置ファイル指定時は config/app.php の版表記を静的に読み、版ごとの指紋と照合します。DB のみの場合は複数の版で必須列が共通するため、確認した版を `--source-version=2.00.125` のように渡してください。設置ファイルを省略した場合は、DB で確認できる範囲の判定になります。既知の公開保留理由がなければ公開設定を引き継ぎ、ファイル未照合を警告します。一度判明した設置ファイルの問題は、その後ファイル指定を省略しても保留理由に残ります。本番切替前にはファイル付きで再実行してください。
- 有効なプラグイン、変換できなかった独自テーマ、未対応の種類・入力制限・アクセス条件・置換タグ、設定未完了の reCAPTCHA、未対応の HTML 等があるフォームは下書きにします。旧プラグインのコード・設定データの移植は対象外です。無効なものも含めてプラグイン一覧と標準外テーブル名を表示します。旧 reCAPTCHA の有効状態を引き継ぎます。利用している場合は新環境の RECAPTCHA_SITE_KEY と RECAPTCHA_SECRET を設定してください。旧キー、シークレット、独自列の値は新 DB に保存しません。
- 欠損した項目、重複・予約済み URL、公開システムと競合する入力名も診断します。元 URL を割り当てられないフォーム、元のフォーム定義が削除された履歴には下書き用の仮 URL が付きます。元データの位置を記録した上で、既存フォームとの衝突を避けます。
- 公開前に修正が必要な事項は各フォーム定義の `issues` に、目視確認が必要な警告はフォームの編集画面に表示します。移行用複製の設定や移植したコードを修正し、再診断で該当項目が解消したことを確認してください。公開保留のないフォームでも、運用で使っていた URL・文章・画面・メール・CSV を見本と照合してください。

旧公開URLの設置先を `--source-base` で指定すると、新旧の入口をフォームごとに照合できます。[公開URLの引き継ぎ](URLS.md)

## 取込と再実行

```sh
php artisan easymail:import --source-root=/backup/EasyMail
php artisan easymail:import --source-root=/backup/EasyMail --attachments=/private-backup/old-files --json
```

フォームで現在使っていない共通項目も、旧版で削除されていなければライブラリへ移します。同梱標準版と同じ項目は重複登録を省きます。`--form` では指定フォームに使われる共通項目だけを対象にします。

旧 ID と新 ID を対応付けます。同じ移行元の再取込では旧 ID が同じレコードを更新し、変更されたフォーム定義には新しい版を記録します。運用元の異なるサイトは別の MailForm DB を用意してください。再取込では旧側のフォーム設定・公開状態を再適用するため、最終取込が完了してから新側での編集を開始します。全件取込では、旧側で削除されたフォームを公開停止にして旧 ID を報告します。新環境でアーカイブしたフォームの公開停止、消去済み履歴の消去状態を維持します。旧側から消えた受付を新側で物理削除する処理はありません。

履歴には受付日時、当時のタイトル・順序・回答、メール件名・宛先などの標準履歴列を保持します。対応版の `histories.content` は項目名を持たない JSON 配列です。現行項目に一意に対応する回答にはその項目キーを使い、削除済みの項目や同名項目には履歴内の順序からキーを割り当てます。元 JSON は常に `snapshot.legacy_history.content` に保存します。独自形式や壊れた JSON には警告を出し、解釈できた列だけを展開します。旧標準版が保存していない送信済みメール本文は復元できません。履歴取込では配信用のレコードを作成しません。

添付は実ファイルを SHA-256 で照合して非公開の `local` ディスクへ取り込みます。旧版の 40 文字の乱数名の連結とカンマ区切りに対応します。2.00.124・2.00.125 では、拡張子のない保存名と拡張子付きの保存名が区切りなしで並ぶ場合も照合します。実ファイルや以前の取込記録から複数の解釈が成り立つときは警告に残し、既存のコピーを保全します。元の利用者ファイル名や入力欄との対応を確定できない場合は旧保存名を使用し、履歴単位で紐づけます。欠損・不正パスの件数はフォームの警告で確認できます。欠損を復元して再実行すれば、すでに取り込んだ履歴に添付が追加されます。

再取込は全旧IDを読み直します。更新日時が変わっていない修正や、その間に追加された受付も取り込めます。同じ旧履歴の添付が差し替えられた場合は新しい内容に更新し、旧履歴から参照が外れた添付は移行先の紐付けを外します。新しい紐付けを確定した後、参照のなくなった移行用コピーを非公開ストレージから削除します。旧DBに名前が残っていて複製の実ファイルだけが欠けた場合は、前回のコピーを保持します。不正な添付参照を含む履歴は以前の紐付けを保持して照合に出します。

## 初回取込と最終取込の照合

`--verify-only` は固定した旧DB・添付複製を、新DBと新側の実ファイルに突き合わせます。取込前と取込後で同じオプションを使い、JSONを公開領域外に保存してください。例では担当者だけが読める記録用ディレクトリに移動してから、MailFormの `artisan` を絶対パスで実行します。

```sh
umask 077
php /srv/mailform/current/artisan easymail:import --source-root=/backup/EasyMail --verify-only --json > before.json
php /srv/mailform/current/artisan easymail:import --source-root=/backup/EasyMail --json > import.json
php /srv/mailform/current/artisan easymail:import --source-root=/backup/EasyMail --verify-only --json > after.json
```

初回や新着分がある取込前は終了コード2が想定されます。各コマンドの終了コードを個別に記録します。取込レポートの `history_count` と `resolved_files` は処理時に読めた旧履歴・旧添付の件数です。取込後は照合の終了コード0と `reconciliation.ok` が `true` であることを確認します。終了コード2は要照合、1は接続・設定・排他などの実行エラーです。フォームごとの下書きやテーマの目視確認待ちがあっても、照合が一致すれば続行します。照合の間は複製を固定し、新側での編集・試験送信・消去を止めてください。最終照合は `--form` を省いて全件で行います。

`source_history_count` は旧DBの対象履歴の総件数です。フォーム別件数との一致を確認し、フォームIDを特定できない履歴がある場合は全件取込を停止します。`reconciliation.forms[]` の各行には旧フォームID、対応する新フォームID、フォーム定義・公開状態の比較結果、次の集計があります。

| JSON項目 | 数え方と確認する内容 |
| --- | --- |
| `source` | 旧履歴をID単位で `matched`（一致）、`changed`（更新が必要）、`missing`（未取込）、`pending_purge`（新側で消去待ち）、`purged`（新側で消去済み）に分けます。合計が `histories` です。`last_source_id` はこのフォームで読んだ最大の旧履歴IDです。 |
| `absent_from_source` | このフォームで以前に取り込んだ履歴のうち、今回の複製に同じフォーム・旧履歴IDの組がない件数です。`retained` と `pending_purge` は要照合です。複製の取り違え・欠落・旧側の削除を確認します。消去対象と確認できた分は新側の通常の履歴削除を使い、消去済みの記録を再照合できます。 |
| `new_only` | 旧IDを持たない新側独自の受付です。`retained`、`pending_purge`、`purged` を別々に示します。全件照合では新側で作ったフォームも `form_state` が `new_only` の行に出ます。ステージングの試験分や切り戻し時の受付を数える際に使えます。 |
| `files` | 保持対象の旧履歴にある有効な保存名を履歴内で重複を除いて `expected` に数えます。`verified` は保存名、リンク先、サイズ、旧・新ファイルのSHA-256が一致した件数です。`source_unavailable` は旧複製の欠損、`unsafe` は不正参照、`target_missing` は新側のリンク・実体の欠損、`changed` は内容・保存先等の相違です。`extra_links` は余分な紐付け、`unlinked_copies` は対象履歴の専用ディレクトリにある参照のない移行用コピーです。 |
| `differences`、`examples` | 差異の種類ごとに該当する履歴件数と、最大20件の旧履歴IDを示します。 |

旧側で消えた履歴を保存方針に従って新側に保全する場合、照合は引き続き2になります。保全対象の旧ID・件数・理由を記録し、未取込や添付欠損など他の差異がすべて解消したか確認して、担当者が切替可否を判断します。

一致の判定では履歴の所属、受付・更新日時、保存した旧標準列、当時の項目順・タイトル・型と回答を比較します。消去済みの履歴は回答や添付が復活していないことを確認します。消去待ちは通常の削除処理の完了後に再照合してください。新側の試験受付や過去に消去済みの旧IDは件数に残ります。バックアップの識別子、取得時刻と停止時刻、実行オプション、各終了コードをレポートと一緒に記録してください。

最終取込でも全履歴を読み、照合では添付を読み直します。事前に本番相当の複製でバックアップ取得・復元・取込・照合にかかる時間を計り、受付停止時間を見積もってください。

## 切替

1. 代表フォームを取り込み、旧 URL・項目順序・公開条件・必須エラー・メール内容・履歴 CSV と添付を比較します。試験送信時の SMTP はテスト用の宛先に限定します。
2. 旧サイトの受付・編集を停止し、処理中の送信が終わってからDBと添付を同じ時点で退避します。複製を更新し、同じ接続先・ファイル指定で取込前照合、全件取込、取込後照合を実行します。旧側の件数と各フォームの照合結果、公開保留と警告の対応を確認してからURLを切り替えます。
3. 切り戻し時は新側の受付と送信処理を止め、切替後の受付・添付・配信状態を保全し、旧側へ戻す分を照合します。旧システムは検証完了まで読み取り専用で保管してください。
